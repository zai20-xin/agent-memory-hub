# 架构与接入方式（Architecture）

> **配套文档**：本文是 `hygiene-protocol.md`（规则）的落地篇，讲"目录长什么样、Agent 怎么接进来、谁能写什么"。
> **核心设计原则：治理中枢必须是 agent 无关的**——换任何一个 agent 工具，记忆中枢不搬家。

---

## 一、为什么中枢要 agent 无关

多 Agent 环境有一个隐蔽的陷阱：**把治理中枢（画像、协议、台账）放在某个 agent 自己的目录里**（如 `~/.某agent/memory/`）。这个 agent 一旦停服、卸载、更换，全部共享记忆跟着迁移，成本极高，且迁移窗口期内所有 agent 的画像引用全部失效。

正确做法：共享资产放在一个不属于任何 agent 的中立目录，默认：

```
~/.agents/memory/          ← 记忆中枢（agent 无关）
├── user-profile.md        # SSOT 完整画像（唯一真身）
├── user-profile-quick.md  # 精简版画像（派生副本，唯一）
├── hygiene-protocol.md    # 记忆卫生协议
├── agent-registry.md      # Agent 台账（谁接入、读写规则）
├── memory-revisions.md    # 修订档案
├── tools/                 # 审计脚本等
└── archive/               # 冷库 + 索引 + 台账（audit-log / metrics / 周检报告）
```

> 该目录与 skills 真身目录（如 `~/.agents/skills/`）平级，语义一致：**都是"agent 的公共资产"，不是"某个 agent 的私有资产"**。

## 二、两种接入方式

### 方式 A：软链接入（推荐，适用于支持任意路径引用的 agent）

在各 agent 的主目录建一个指向 SSOT 的符号链接：

```bash
ln -s ~/.agents/memory/user-profile.md ~/.agent-a/user-profile.md
ln -s ~/.agents/memory/user-profile.md ~/.agent-b/user-profile.md
```

优点：改真身，所有接入方零延迟同步；审计脚本可用 md5 校验一致性。

### 方式 B：AGENTS.md 指针接入（适用于不支持软链的 agent）

在 agent 的全局规则文件（如 `AGENTS.md` / `CLAUDE.md`）里写明画像路径，会话内引导读取：

```markdown
## 用户画像
用户画像唯一真身：~/.agents/memory/user-profile.md
会话涉及用户偏好、历史项目、个人事实时，先读该文件。
```

优点：不依赖文件系统软链权限；缺点：同步靠"引导读取"而非硬保证，审计脚本只能检查规则文件是否声明了路径。

### 精简版（quick）双轨制

SSOT 会长到 40KB 级别，不适合每次全量注入。因此维护一份裁剪过的精简版（3~4KB），大多数会话只读 quick 版，需要细节时才读真身。

| 规则 | 说明 |
|---|---|
| quick 版是**派生副本**，永远不允许出现两份"完整真身" | 冲突时以 SSOT 为准 |
| 真身不动时优先更新 quick 版 | 降低 SSOT 被频繁改写的漂移风险 |
| 审计脚本检查 quick 版在位且非近空 | 缺失即 🟡 告警 |

## 三、Agent 分类与读写边界

不是所有 agent 都值得接入画像。按角色分六类，台账（`agent-registry.md`）逐个登记：

| 角色 | 读写规则 | 典型场景 |
|---|---|---|
| **主力 + 治理中枢** | 热记忆自治；**额外承担周期治理任务**（哨兵/医生） | 日常用得最多的 agent，治理是"兼任"而非"新增一个 agent" |
| **第二主力** | 热记忆自治；画像软链接入 | 另一个高频工具 |
| **低频** | 热记忆自治；画像软链接入 | 偶尔用，允许不活跃 |
| **只读监控** | **只读，禁止外部写入**（用户拍板的约定） | 第三方/演示用途的 agent |
| **独立自治** | 不接画像，只有自己的开发偏好 | 纯代码工具，无用户画像需求 |
| **退役封存** | 整目录只读封存，零写入 | 停服/弃用的 agent |

**边界铁律：任何 agent 不越权写其他 agent 的热记忆。** 中枢只拥有：SSOT、协议、台账、归档索引、审计脚本。各 agent 的 MEMORY.md / 日记 / 项目文档是各自领地。

> 为什么不设一个独立的"治理 agent"？单一 agent 停服会迫使整套治理体系迁移。**让主力 agent 兼任治理，少一个进程、少一个故障点。**

## 四、接入矩阵（参考案例）

以下是一套四工具环境的接入配置，可作参考范本：

| Agent | 角色 | 接入方式 | 记忆位置 |
|---|---|---|---|
| agent-a | 主力 + 治理中枢 | 软链接入 | `~/.agent-a/`（MEMORY.md + memory/ + 错误台账 + 方法索引） |
| agent-b | 第二主力 | 软链接入 | `~/.agent-b/memory/`（按项目分日期笔记） |
| agent-c | 第三主力 | AGENTS.md 指针 + 软链 | 会话库（自管勿动）+ 全局规则声明路径 |
| agent-d | 低频 | 软链接入 | `~/.agent-d/` |

接入完成后，跑一次审计验证：

```bash
python3 tools/memory-audit.py --hub ~/.agents/memory
# 预期：接入的软链全部 🟢 且 md5 一致
```

## 五、故障模式速查

| 症状 | 根因 | 处置 |
|---|---|---|
| 某 agent 不知道最近发生的事 | 它的热记忆超 8KB，新事实被淹没/或它没更新自己的日记 | 哨兵体积告警 → 瘦身手术；检查该 agent 日记更新 |
| 画像在不同 agent 嘴里不一样 | 出现了第二份真身（有人把软链换成了实体文件并改写） | 审计 md5 校验发现 → 按第四節修正协议处理 |
| 治理任务连续多天没跑 | "全绿零痕迹"，无法区分全绿与未运行 | 心跳机制：全绿也必须留痕 |
| 共享资产越改越乱 | 缺少变更分级，所有变更堆在一起等审批 | 变更分级（协议第六节） |
